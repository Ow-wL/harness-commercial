## 2. 바로 고칠 가치가 있는 것

### 2-1. 정적 파일 압축 없음 **[확인]**
운영에서 `Accept-Encoding: gzip, br`로 요청해도 `Content-Encoding` 헤더가 없고 JS·CSS·GeoJSON이 원본 크기로 내려온다. FastAPI `StaticFiles`는 압축하지 않고 Cloud Run도 자동 압축하지 않는다. 첫 분석까지 받는 양 약 1.38MB가 gzip만으로 약 0.40MB가 된다(로컬 `frontend/dist` 기준 측정).

| 파일 | 원본 | gzip |
|---|---:|---:|
| `index-*.js` | 524,857 B | 156,568 B |
| `인천_행정동경계_2026-*.geojson` | 610,826 B | 185,899 B |
| `인천_시군구경계_2026-*.geojson` | 164,698 B | 47,125 B |
| `index-*.css` | 76,730 B | 13,345 B |

**[판단]** Starlette 기본 `GZipMiddleware`(최소 크기 지정) 한 줄로 해결된다. `/analyze` JSON(약 7.8KB)도 함께 줄어든다. 검증은 E(Docker build·runtime 파일 목록)와 C(헤더 계약 테스트, `smoke_api.py` 헤더 검사에 `Content-Encoding` 추가).

### 2-2. README가 운영 상태와 다름 **[확인]**
`README.md` 4~5행이 "v0.4 현재 운영", "v0.5 계열 운영 미배포", "8차 UI/UX 개선 진행 중 … 운영 미배포"다. 실제는 앱 v0.0.13 + 엔진 v0.5.1 운영. `CLAUDE.md`·`docs/TASKS.md`는 맞고 README만 낡았다. 9행 "지도 범위 맞춤 … 운영 미배포"도 같은 상태.

### 2-3. 결과를 공유·재방문할 수 없음 **[확인]**
새로고침하면 결과가 사라지고 URL에 상태가 없다(`URLSearchParams`·`history` 사용 없음, 결과 캐시는 메모리 LRU 12). **[판단]** 좌표·업종·반경(+비교 B)을 쿼리스트링에 싣고 첫 로드 때 복원하면 백엔드 변경 없이 "링크 보내기"와 "다시 열기"가 된다. 최근 분석 기록(로컬 저장, 익명)도 같은 작업에서 다룰 수 있다. 데이터·엔진 버전이 바뀌면 복원 결과가 달라질 수 있으므로 복원은 "같은 조건으로 다시 분석"이어야 한다(저장한 점수를 보여 주지 않는다).

### 2-4. 엔진 면책 원문이 화면 메시지와 충돌 **[확인]**
화면은 "순위가 아닙니다"(요약 하단, 점수 비교 대상 설명, 첫 방문 안내)라고 반복하지만, 상세 근거 맨 아래 엔진 면책 원문은 "본 점수는 공공데이터 기반 상대 순위이며 매출을 보장하지 않습니다"다. 원문 보존 정책(§19.6, D-031 이전 결정)은 유지하더라도 두 문장이 같은 화면에 있다. **[판단]** 팀에 v0.6 면책 문구 수정을 요청하고, 그때까지 원문 아래에 "엔진 원문의 '상대 순위'는 백분위 계산 방식을 뜻하며 후보지 순위가 아닙니다" 한 줄을 화면 주석으로 둔다(원문은 바꾸지 않는다).

### 2-5. favicon·meta·robots 없음 **[확인]**
`/favicon.ico`·`/robots.txt`·`/manifest.json` 404, `<meta name="description">`·OG 태그·`<link rel="icon">` 없음(`frontend/public` 디렉터리 자체가 없다). 링크 공유 시 제목만 보인다. **[판단]** 작은 작업이지만 `backend/app/frontend.py`의 루트 파일 서빙·E 검증(dist 파일 목록 테스트)과 맞물린다.

### 2-6. 문구 **[확인]**
주소 검색 실패 메시지 "‘부평역’로 찾은 주소가 없습니다"에서 조사가 어긋난다(인용부호 뒤라 조사 선택이 안 된 형태). "‘부평역’(으)로" 또는 "검색어 ‘부평역’에 맞는 주소가 없습니다"처럼 조사를 피하는 문장이 낫다.

## 3. 운영·개발 체계에서 약한 곳

### 3-1. 데이터 갱신이 곧 두 분기 뒤처진다 **[확인]**
운영 데이터는 상가 2026-06-30, 인구 패널 2026-08-31, 생활이동 2026-08. `docs/IMPROVEMENT_PLAN_2026-10.md` 2-1 기준 상가 차기 파일 등록 예정 2026-10-31, 인구 2026-09 파일은 이미 공개. 묶음 C(데이터 버전 구조·ETL 사본·검증 스크립트)는 운영 반영됐지만 **새 데이터 버전을 실제로 만들어 적용한 적이 없다**. **[판단]** 첫 실전 갱신(수집 → 검증 → 차이 보고서 → 새 리비전)이 다음 운영 과제 중 가장 크다. 엔진·golden은 그대로 두고 `data/versions/<id>/`로 간다(D-006 개정).

### 3-2. CI 없음 **[확인]**
`.github/workflows` 없음. 모든 검증이 로컬 `scripts/check`와 기록 규칙에 의존한다. **[판단]** push마다 빠른 단계(integrity·patch-notes·backend·frontend typecheck/lint/vitest)만 자동으로 돌려도 기록 규칙의 신뢰도가 올라간다. golden·엔진 4단계는 시간이 길어 수동 유지 또는 야간 1회.

### 3-3. 확장 한계와 상시 과금 **[확인]**
Cloud Run: 최대 인스턴스 1, 최소 인스턴스 1, 동시 요청 4, 1 vCPU·1Gi, CPU 상시 할당, startup CPU boost. 메모리 캐시·단일 워커 구조(D-016)의 귀결이다. **[판단]** 동시 사용자 5명부터 대기가 생기고, 시연·발표처럼 접속이 몰리는 날에는 사전에 알아야 한다. 최소 인스턴스 1 + CPU 상시 할당은 트래픽이 없어도 과금된다. 디스크 캐시(D-016 재검토)나 warm 결과 직렬화 없이는 인스턴스를 늘릴 수 없다.

### 3-4. 공개 API에 사용량 제한·보안 헤더 없음 **[확인]**
`/analyze`·`/nearby-stores`는 인증·속도 제한이 없다. 응답에 `Strict-Transport-Security`·`X-Content-Type-Options`·`Content-Security-Policy` 없음. **[판단]** 3-3과 합치면 스크립트 몇 개로 서비스가 느려질 수 있다. IP 단위 간단한 제한(또는 Cloud Armor)과 기본 보안 헤더는 비용이 작다. CSP는 NAVER SDK 도메인 목록이 필요해 별도 확인.

### 3-5. 사용 현황을 볼 수 없음 **[확인]**
분석 횟수·업종·구 분포·오류율을 볼 장치가 Cloud Run 요청 로그뿐이다. **[판단]** 개인정보 없이 서버 로그에 (업종, 구, 반경, 결과 코드, 지연)만 구조화해 남기면 다음 개선 우선순위를 데이터로 정할 수 있다. 클라이언트 분석 도구는 넣지 않는다.

### 3-6. 작은 정리 **[확인]**
`.claude/launch.json`(git 제외)에 지난 세션의 임시 경로를 가리키는 실행 설정이 쌓여 있다.

## 5. 측정·확인 기록

- 응답 헤더(`GET /`): `cache-control: no-cache`, `etag`, 압축·보안 헤더 없음. `/assets/*`는 `public, max-age=31536000, immutable`.
- `/analyze` 4건: 부평역 PC방 1km 200/0.24s, 미추홀 카페 300m 200/0.12s, 서울시청 좌표 422/0.09s, 중요도 `stability:5` 200/0.14s. `OPTIONS /analyze` 405.
- 접근성 자동 점검(JS, 결과 화면): 이름 없는 버튼·링크는 NAVER SDK 법적 고지 링크 1개뿐, `img` alt 누락 0, `main` 1·`h1` 1, `lang=ko`. skip link 없음(확인만, 판단 보류).
- 저장소: pytest `def test_` 302개, 프런트 `it/test` 617개(정규식 집계, 실제 실행 건수는 `TASKS.md` 11-6 참고), CI 없음, 브랜치 `master`만.
