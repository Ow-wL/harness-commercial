## 2. 엔진 선택 — 기존 규칙 그대로

- 프로세스당 엔진 하나: `SCORING_ENGINE_VERSION = v0_3(기본) | v0_4 | v0_5`. **코드 기본값은 바꾸지 않았다**(D-024 규칙: 운영 전환은 리비전 환경변수로, 사용자 승인 뒤).
- 운영은 지금 v0.4(2026-10-19 배포)다. v0.5 전환은 무트래픽 리비전 → warm 87/87 → smoke → 승인 뒤 전환(별도 단위, `docs/TASKS.md` 10장).
- 로컬 실행: `SCORING_ENGINE_VERSION=v0_5 python -m uvicorn backend.app.main:app`. `/health engine = {version: "mvp-0.5", radius_options: [300, 500, 1000], default_radius_m: 500}`.
- 프런트 결과 캐시는 응답 `엔진버전`이 바뀌면 전부 버린다(8-D3 기존 동작, v0.4 → v0.5 테스트 추가). 비교 A·B 엔진버전이 다르면 B 계약 오류(기존).

## 3. 팀 v0.5와 웹 v0.5의 차이 — 이유

이름 주의: 팀 번들의 "v0.4"는 **집적 효과**(교수님 피드백 2026-10-16) 변경이고, 웹의 v0.4(`mvp-0.4`, D-024)는 **반경 선택**이다. 서로 다른 변경이다. 팀 v0.5는 팀 v0.4를 포함하고 반경 선택은 없다. 웹 v0.5 = 팀 v0.5 + 웹 v0.4와 같은 방식의 반경 diff.

## 5. 화면 의미 (프런트)

- 비교 기준: 데이터 출처 표·[이 점수는?]·점수 읽는 법에 "인천 158개 행정동 중심점(동네 평균 지점) 대비 — 상업지 후보지끼리의 순위가 아님", 엔진 `meta.정규화_기준` 원문.
- 고객성 근거 줄 "반경 {r} 타겟 연령 거주 N명", 계산 단위 "지점 반경 {r}(행정동 경계 면적 배분, 1인 세대 비중은 행정동 값)". 경쟁성 "반경 {r} {업종} N곳 · 비슷한 업종 포함 약 M곳 · 점포당 잠재수요(거주+종사자) K명".

- 상권 집적도 백분위: "점포가 모인 정도이며 상권 우수성·성공 가능성 순위가 아닙니다". 팀 제안의 "인천 상위 1% 상권" 같은 표현은 쓰지 않았다.
- 임대료: 웹은 임대료를 빼고 계산한다는 기존 설명 + 엔진 `임대료_해석`의 뜻("감당 가능성"이지 "손님 대비 비싼가"가 아님).
- 반경 안내: v0.5는 "고객성(반경 안 인구)·경쟁성과 주변 점포"가 반경을 따른다(v0.4 문구 그대로 두면 틀린 설명).
- 두 위치 비교: v0.3·v0.4의 "같은 행정동이면 고객성은 같은 데이터" 규칙을 v0.5 응답에서는 쓰지 않는다(고객성 인구가 지점 반경 값이라 같은 동이어도 다르다). 같은 동 안내는 "위치 차이는 고객성·경쟁성(반경)과 입지성(좌표)에 나타납니다".
- 점수 ≠ 성공 확률: "분석팀 사후 점검에서도 점수가 높은 곳의 가게가 더 오래 살아남는 관계는 확인되지 않았다"를 점수 읽는 법에 추가(팀 v0.5 변경사항 3-2, 음식 9개 업종 평균 ρ v0.4 −0.089 → v0.5 −0.069 — 수치는 화면에 쓰지 않음).

**기록하는 수치**
- 일평균 방문자와의 순위상관(이상치 제외 38곳): 반경 종사자 0.59, 반경 점포 수 0.55, 반경 거주인구 0.37.
- 반경 점포 수로 설명되는 방문 규모 변동: 로그 회귀 R² 약 0.25(활동인구를 더해도 약 0.29). → "점포 수가 방문 규모를 잘 대신한다"가 아니라 "중간 정도로 따라간다".
- 방문객 20~39세 비중은 반경 거주민보다 평균 약 7.8%p 낮지만, 상권 간 순위상관은 0.54. 연령 차이에는 SKT 가입자 구성(고령층 명의·자녀 회선 등)의 영향이 섞였을 가능성이 있어 **보정 근거로 쓰지 않는다**.
- 일부 조사 상권(번화가·신도시 상업지)에서는 외부 방문자 추정치가 엔진 활동인구(반경 거주 + 종사자)의 약 3~5배였다. 38곳 전체로는 중앙값 약 1.1배(범위 약 0.4~5.5배)이고 주거지 상권은 대체로 1배 안팎이었다. **이것은 전체 상권에 적용할 보정 배수나 실측 수요가 아니다**(외부 방문자 = 눈대중 방문자 × 방문자 비율, 범위도 엔진 반경과 다르다).
- (엔진 쪽 점검, 팀 v0.5 변경사항 3-1) 도시지역 112개 동, 반경 거주인구 통제 편상관 — 집적형 업종 종합점수의 번화가 편상관 v0.4 +0.16 → v0.5 −0.02.

**유지한 것**: 잠재수요 = 거주인구 + 종사자(종사자와의 순위상관이 가장 높아 방향이 맞다), 연령 보정 없음, v0.5 계수·점수 구조 그대로.

**화면 문구**(공개 범위가 "사이트 금지·발표만 출처와 함께"라 수치 없이 정성 문장만): 경쟁성 해석의 한계 첫 줄 —
"번화가·신도시 상업지는 외부 방문객이 많아, 거주인구와 종사자를 기준으로 계산한 경쟁성(점포당 잠재수요)이 실제 수요를 충분히 반영하지 못할 수 있습니다."
(프런트 테스트가 화면 소스·fixture에 "지오비전·퍼즐·SKT·3~5배·1/3~1/5·18명·외부방문자"가 없는지 검사한다.)

**"퍼즐 승인 대기" 문구 정리**: 팀 v0.5 문서(변경사항 2장 "방문 인구: 지오비전 퍼즐 승인을 기다리는 중", 정리본 6장 "(지오비전 퍼즐 대기)")와 `config.py` 주석은 현재 상태와 맞지 않는다 — 퍼즐 화면 기록은 끝났고(2026-09-24~10-23, 43곳), 서비스가 2026-11-15에 끝나 데이터원으로 연결하지 않는다. 팀 원본은 수정하지 않고(원본 보호) 웹 문서·화면에는 "승인 대기" 표현을 쓰지 않는다. `config.VISIT_COL`·`VISIT_COEF`(방문인구 자리)는 엔진에 남아 있지만 웹은 `DEMAND_COLS`(거주 + 종사자)만 넘긴다.

## 9. v0.5.1 — 분동 배분 결함 수정 (2026-10-24, D-029)

Codex 검수 지적. 상세(원인·재현·가정 비교·차이 표): `docs/spikes/v0_5_1-split-dong/README.md`, 차이 원표 `diff.md`.

- **결함은 팀 엔진에서 왔다**: `DongAreas`가 신설 분동을 모체 경계로 연결하며 가중치에 분동 인구비를 곱하는데, 패널 값이 이미 분동별이라 인구비가 두 번 들어간다(같은 총량에서 배분 약 절반). 원천 규칙은 `etl_sgis.attach`(모체 통계 분할)다.
- **버전 규칙**: 팀 원본·웹 v0.5·golden v0.5(팀 결과)는 그대로. 수정은 새 엔진 `v0_5_1`(`mvp-0.5.1`) — `etl_boundary` 비율 한 줄 + 엔진버전. `SCORING_ENGINE_VERSION=v0_5_1`.
- **가정**: 모체 경계 안 균등 거주 → 모체 면적 비율만(분동 전후 총량 보존). 2026 자식 경계로 따로 배분하는 대안은 아라동에서 ±3%로 비슷하고 운서동에서 크게 다르다(공항·해역) — 경계 출처를 섞는 설계 변경이라 **다음 과제**.
- **차이**: 비교 분포가 바뀐 중심점은 아라1·2·운서1·2동(세 반경)과 원당동(500·1,000m). 158개 중심점 웹 분석(144곳 × 29업종): 바뀐 관점은 고객성·경쟁성뿐, 500m 종합 변경 2,524/4,176건·평균 0.28점·최대 11.5점(1km 최대 15.2점, 아라동 지점). 부평역 500m는 13개 업종 종합 ±0.1~0.3점, PC방 61.6·77.5·31.9·66.4·63.9·종합 60.6(v0.5 60.7), 상위 3 순서 그대로. 웹 경로(임대료 미연결) 부평역 PC방 종합은 v0.5와 같은 방식으로 안정성만 다르다.
- **화면**: 응답 형태가 v0.5와 같아 프런트는 `isAreaWeightedEngine`(mvp-0.5·mvp-0.5.1)으로 같은 설명을 쓴다. 엔진버전이 바뀌면 결과 캐시는 기존 규칙대로 전부 버린다.
