## 2. 확정 후보 규칙 (UI 트랙)

### 2.1 결과 요약 위계 — 방향 2 「요약 보고서형」

지금 shell(헤더 56px · 패널 480/560px · 지도)과 토큰(§17)은 그대로 두고 패널 안의 순서만 바꾼다. 새 색 없음.

```
조건 한 줄(행정동 · 업종 · 반경)  [조건 바꾸기]
헤드라인 1줄                         ← 2.3
주의 요약 띠(0~5줄, 항상 펼침)        ← 2.2
종합 적합도 44px · "5대 관점 가중평균 · 순위 아님" [이 점수는?]
5대 관점 막대 + 막대 아래 근거 줄     ← 2.5
충족 1줄(충족률 · 5칸 · 가중치 · 진입장벽)
탭: [근거] [주변 점포 N] [주의·한계 N]
[다른 위치와 비교] [조건 바꾸기]
출처·방법(접힘) · 면책 1줄(항상)
```

유지(바꾸지 않음): 색 토큰 전부, 타이포 scale, 4px 간격, 패널·막대·본문 폭, 헤더 56px, breakpoint, 막대 고정 순서·0~100·50 기준선, radar 금지, 미산출 빗금, 카드 그림자 없음, 접근성 규칙(§15). 근거: 대비·폭·포커스는 6-2·6-3·6-4에서 이미 실측으로 맞춘 값이다.

시각 시안: 저장소 밖 정적 HTML(검수 보고에 경로 첨부). 데스크톱 D-A 분석 전 / D-B 단일 / D-C 비교, 모바일 M-A~M-C 단일 / M-D 비교. 프레임마다 "값 출처" 줄이 있고 설명용 예시 값은 따로 표시한다.

### 2.2 주의 요약 띠 — 판단에 중요한 사실은 항상 요약 1줄

**원칙**: 병목·학교 규제·미산출·낮은 신뢰도·비교 계산 구성 차이는 **항상 요약 1줄로 보이고**, 설명만 탭·펼침으로 간다. 띠는 헤드라인 바로 아래(종합 숫자 위). 각 줄 = 모양 아이콘(warning `!`, info `i`, 구성 차이 `†`) + 40자 이내 + "›"(해당 탭으로 이동). 0줄이면 띠를 두지 않고 "특별한 경고가 없습니다"는 주의 탭에만 둔다.

| 항목 | 표시 조건(응답 값) | 요약 문구 | 톤 | 상세 위치 |
|---|---|---|---|---|
| 병목 | `병목_지표` 점수 < 25 | "{관점} {점수}점 · 병목 기준(25점 미만) — 종합과 별개 위험 요인" | warning | 주의 탭(§8.3 대체 문장 그대로) |
| 병목 25 이상 | — | **띠에 넣지 않는다.** 헤드라인 "…가장 낮습니다"와 막대 라벨 "가장 낮음"으로 충분 | — | — |
| 학교 규제 | `초보자_접근성.입지_규제` 있음 또는 `주변_학교.학교수 > 0` | 0곳 "학교 주변 규제 업종 · 300m 안 초·중·고 0곳" / N곳 "300m 안 초·중·고 N곳 · 교육지원청 확인 필요" | 0곳 info / N곳 warning | 주의 탭 + 접근성 상세 |
| 미산출 | `지표[].score === null` | "안정성 미산출 · 종합에서 제외" / 경쟁성 0곳 "반경 {r}m 안 {업종} 0곳 · 경쟁성 미산출" | warning | 근거 탭 해당 관점 |
| 낮은 신뢰도 | `confidence === 'low'` | "{관점} 신뢰도 낮음(엔진 판정)" — **원인을 적지 않는다.** 그 관점이 미산출이면 별도 줄 없이 미산출 줄 끝에 "· 신뢰도 낮음" | warning | 근거 탭 |
| 기타 엔진 경고 | `displayWarnings` 출력(병목 대체 적용 뒤) 중 위에 안 잡힌 것. **단 병목 관련 엔진 문장은 띠에 원문으로 올리지 않는다**(아래 규칙) | 원문 1줄(길면 말줄임 + ›) | warning | 주의 탭 전문 |
| 비교: 계산 구성 차이 | `overallCompositionNotice !== null` | "† 종합 계산 구성이 다릅니다 · A 5개 관점, B 4개(안정성 미산출)" — **비교 띠 첫 줄** | info | 각주 |
| 비교: 위치별 | 위 규칙을 A·B에 각각, "A "/"B " 접두 | "B 경쟁성 24.4 · 병목" | 규칙 그대로 | 주의 A/B 탭 |
| 비교: 같은 구·동 / 반경 겹침 | `sameAreaNotice`·`radiusOverlap` | "같은 구 · 시장성·안정성은 같은 데이터" / "반경 겹침 · 직선거리 322m" | info | 표 아래 |

규칙
- 순서: † → 병목 → 미산출 → 학교 → 신뢰도 → 기타. 최대 5줄, 넘치면 "주의 N건 더 보기 ›".
- **낮은 신뢰도의 원인을 단정하지 않는 이유**: 엔진 `_conf`는 폴백 레벨·입력 유무와 coverage(0.8/0.5 미만) 두 요인을 합쳐 등급을 낮추므로 응답만으로 원인을 가를 수 없다. 웹 경로에서 `low`가 실제로 나오는 경우는 안정성 미산출(구 표본 < 30)과 경쟁성 0곳(엔진이 `confidence="low"` 명시) 둘뿐이라 대부분 미산출 줄과 겹친다.
- **주의 탭 목록은 지금 `lib/warnings.ts`의 `displayWarnings`·`dataLimits` 출력 그대로**다(병목 경고 1건만 구조화 문장으로 대체, 나머지 엔진 원문, 미산출 안정성 note 숨김, 해상도 칩은 산출 관점만). 띠는 그 위의 요약일 뿐 탭 문장을 바꾸지 않는다. 바꾸는 것은 `dataLimits`의 **해상도 안내 줄("…단위로 계산했습니다")만** 제거(근거 줄 "구 단위"와 중복)이고, 신뢰도 낮음·임대료 제외 줄은 유지한다.
- **병목 원문 예외**: 엔진 병목 경고("{관점}이(가) 인천 하위 N%로 …")는 관점 점수를 순위처럼 읽게 한다(DESIGN §8.3). 지금 `displayWarnings`는 "병목 점수 < 25 이고 `경고[0]`이 '{관점}이(가) '로 시작"일 때만 구조화 문장으로 바꾸고, 조건이 맞지 않으면 원문을 그대로 둔다. 띠는 병목을 **구조화 필드(`병목_지표`·score)로만** 표시하고, 조건 불일치로 원문이 남은 병목 문장은 띠의 '기타' 줄로 올리지 않는다 — 그 원문은 주의 탭에만 지금처럼 남는다(탭 동작 불변). 미산출 안정성 note도 지금처럼 숨긴다.
- 띠·헤드라인·근거 줄 문장은 구조화 필드로 새로 만든 요약이다. 엔진 원문은 탭에 남지만, 위 병목 대체(§8.3)와 미산출 안정성 note 숨김(§8.4) 두 예외는 탭에서도 지금 규칙 그대로다(원문이 그대로 보이는 것이 아니다).
- 모바일 지도 sheet peek에는 띠 첫 줄만.
- 테스트 fixture: 부평역 PC방(학교 0곳 info 1줄 — 경쟁성 30.2는 25 이상이라 띠 없음), 부평역 네일숍(병목 1.2·미산출·신뢰도), 강화읍 B(† + 안정성 미산출), 송도2동(경쟁성 0곳 미산출). 줄 수·순서·문구와 금지 표현(순위·상위 N%·성공 확률·미산출을 0으로)을 고정한다.

### 2.3 헤드라인 문장 (`lib/headline.ts` 후보, 응답 값만)

| 상황 | 문장 |
|---|---|
| 산출 5개, 동점 없음 | "{최고}이 가장 높고, {병목}이 가장 낮습니다" |
| 최고 동점 | "{최고}·{동점 관점}이 가장 높고, …" — 엔진 `최고_지표`를 앞에, 나머지 동점은 관점 고정 순서 |
| 병목 동점 | "…{병목}·{동점 관점}이 가장 낮습니다" — 같은 규칙 |
| 모두 같은 점수 | "다섯 관점 점수가 모두 {점수}점입니다" |
| 산출 2~4개 | 위 문장 + " · {미산출 목록} 미산출(종합에서 제외)" |
| 산출 1개 | "{관점}만 산출했습니다({점수}점) · 나머지 4개 미산출" |
| 산출 0개(`종합.점수 === null`) | "산출한 관점이 없어 종합 점수를 내지 않았습니다" (종합 자리 "산출 불가" 유지) |
| 사용자 가중치 | 문장 끝 "(사용자 가중치 적용)" |

"높다/낮다"는 그 위치 안 5개 관점 사이의 비교이며 다른 위치·순위와 무관하다는 설명을 [이 점수는?] 첫 줄에 둔다. 동점·부분 미산출 fixture가 실제 응답에 없으면 fixture 값을 변형하되 **표시 테스트 전용**임을 파일명에 적는다.

### 2.6 지도 맞춤 정책 (8-B0 반영)

**용어**
- **맞춤(fit)**: 대상(단일 = 반경 원, 비교 = A∪B 원)의 bounds가 **사용 가능 영역 U** 안에 들어가는 **가장 큰 정수 zoom**으로 옮기고, 대상 중심을 U 중심에 놓는다.
- **U**: `section.map` 사각형에서 우리 오버레이(범례·안내 칩·점포 막대·반경 chip·맞춤 버튼)의 실제 DOM 사각형과 SDK 컨트롤(확대 컨트롤, NAVER 로고·축척, 저작권 표기를 켠 경우 그 표기)을 뺀 사각형. 장애물마다 면적을 가장 적게 잃는 변 쪽으로 밀어 넣고 8px 띄운다. 맞춤 때마다 DOM에서 다시 잰다. SDK 컨트롤 DOM을 못 찾으면(8-B0: 지도 생성 직후 1/4회 아직 없었음) 실측 크기의 사각형을 같은 자리에 둔 것으로 대신한다 — 확대 컨트롤 SMALL 50×79(오른쪽 위), 로고·축척 158×17(오른쪽 아래). 모바일 sheet는 지도 밖이다(실측: 4px만 겹침).
- **잠금**: 사용자가 지도 zoom·위치를 직접 바꾸면 켜진다. 감지는 SDK 이벤트 `zooming`(휠·± 컨트롤)과 `dragstart`(드래그) — 우리 호출(`fitBounds`·`setZoom`·`setCenter`·`panBy`·`panTo`)은 이 두 이벤트를 내지 않는다(8-B0). 터치 pinch는 미검증(3.8).
- **확대 컨트롤**: SDK `zoomControlOptions.style = SMALL`(50×79, 슬라이더 없음) — 검수 결정(2026-10-14). 기본 LARGE(50×238)는 태블릿 319px 지도 높이의 75%를 차지한다.

**우선순위표 (위가 이긴다)** — 단일 사건(1·2·3·4·7·8)은 8-B1, 비교 사건(1의 "두 위치 모두 보기"·5·6)은 8-B2에서 구현한다.

| 순위 | 사건 | 동작 | 잠금 | 단계 |
|---|---|---|---|---|
| 1 | "범위에 맞추기" / "두 위치 모두 보기" 버튼(우리 DOM, 키보드 접근) | 무조건 fit(단일: 원 / 비교: A∪B) | 해제 | 8-B1 / 8-B2 |
| 2 | 새 위치 선택(클릭·주소·좌표) | 새 원이 지금 화면에서 이미 완료 조건(아래)을 만족하면 이동 없음, 아니면 fit(원이 U보다 크면 zoom-out도 fit) | 해제 | 8-B1 |
| 3 | 반경 단계 변경(8-D 뒤) | 2와 같은 규칙(새 원) | 해제 | 8-D 뒤 |
| 4 | 숨김 복귀(모바일 패널 → 지도, 태블릿 지도 펼치기) | **미뤄 둔 2·3(비교는 5·1)이 있을 때만** 실제 크기 확인 뒤 1회 실행. 없으면 아무것도 안 함 | 유지 | 8-B1(단일) / 8-B2(비교) |
| 5 | 비교 B 선택 | A∪B 맞춤 zoom ≥ 13이면 fit(A∪B), 아니면 B 원에 2 규칙 + "두 위치 모두 보기" 노출 | 해제 | 8-B2 |

**완료 조건(통일)**

| 화면 | 조건 |
|---|---|
| 단일 | 원 bbox ⊂ U(±1px) **그리고** 원 지름 ≥ 0.5 × min(U.w, U.h) |
| 비교(가까움, zoom ≥ 13) | A·B 두 원 bbox ⊂ U |
| 비교(멂) | B 원이 단일 조건 충족 + "두 위치 모두 보기" 버튼 존재 |
| 공통 | 점포 선택·Escape·창 크기 변경 20회 뒤 zoom 불변 |
| 공통 — **SDK 표기 가림 없음** | 우리 오버레이(범례·안내 칩·점포 막대·반경 chip·맞춤 버튼)의 사각형이 NAVER 로고·축척 사각형과 겹치지 않는다(교차 면적 0). 저작권 표기(`mapDataControl`)를 켜는 경우 그 사각형도 같다. 모든 측정 폭 × 화면 상태(분석 전·결과·비교·점포 선택)에서 확인. 8-B0 근거: 스파이크의 모바일 반경 chip 흉내 자리(아래 12px)가 로고·축척과 약 5px 겹쳤다(3.4) |

**판정 기준**: 원 SVG 요소(`Circle.getElement().getBoundingClientRect()`) 사각형으로 판정하고, `map.getBounds()`·`circle.getBounds()`로 계산한 사각형(경도 선형, 위도 Web Mercator)으로 교차 확인한다. 8-B0 재측정 36건에서 두 판정이 모두 같았다. `getProjection().fromCoordToOffset`은 쓰지 않는다(`panBy` 뒤 갱신되지 않음).

**구현 수단 — 단일 원(8-B0에서 검증)**
- zoom은 **직접 계산**한다. 스파이크 `S.fitCustom`과 같은 식:
  ```
  d = 지금 zoom에서 원 지름(px) = max(bounds 계산의 w, h)
  z = clamp(지금 zoom + floor(log2(min(U.w, U.h) / d)), minZoom, maxZoom)
  setCenter(원 중심) → setZoom(z, false) → panBy(Point(지도 중심.x − U 중심.x, 지도 중심.y − U 중심.y))
  ```
  `panBy(+x, +y)`는 보이는 영역을 오른쪽·아래로 옮기므로 원은 화면에서 왼쪽·위로 x, y px 움직인다. 그래서 **(지도 중심 − U 중심)**을 넘긴다. 예: 1280 U 중심 (375, 342.5), 지도 중심 (400, 371.5) → `panBy(25, 29)`. 재측정에서 원 중심 − U 중심 = (0, 0)이 18/18. 세 호출 모두 동기로 끝난다.
- SDK `fitBounds(bounds, margin)`의 zoom 선택은 쓰지 않는다 — 비대칭 margin이면 한 단계 낮은 zoom을 골라 완료 조건을 못 채운다(3.3).
- 2의 "이미 조건을 만족하면 이동 없음"과 6의 "panTo 후 위반이면 fit"은 **먼저 판정**한다: 이동 뒤 원이 조건을 만족할지 계산해 `panTo` 또는 fit 중 하나만 부른다. `panTo`(약 1초 애니메이션) 도중 `setZoom`을 부르면 이동이 중간에서 멈춘다(3.5).
- 숨김(크기 0) 동안에는 맞춤을 미루고, 보이고 `setSize`가 끝난 뒤 1회 실행한다(6-4의 `sized` 흐름 재사용). 숨김 중 `fitBounds`는 오류 없이 **마지막으로 setSize된 크기**로 계산하며, U는 잴 수 없다(3.6).
- `prefers-reduced-motion`: 맞춤은 이미 즉시 이동이라 추가 처리 없음. `panTo`만 해당.

**비교(A∪B) — 8-B0에서 직접 계산은 검증하지 않음, 8-B2 검증 항목**
- 8-B0이 비교에 대해 확인한 것은 **SDK `fitBounds(A∪B, U margin)` 결과뿐**이다(1280 z13, 970·375 z12, 두 원 모두 U 안). 단일 원 직접 계산을 A∪B로 넓힌 식(`z = 지금 zoom + floor(log2(min(U.w / w, U.h / h)))`, w·h = A∪B bounds 사각형)은 시험하지 않았다.
- 8-B2에서 검증할 것: (a) A∪B 직접 계산의 zoom·중심이 두 원 ⊂ U를 만족하는지, SDK `fitBounds` 결과와의 차이, zoom 13 기준 판정이 어느 방식 zoom으로 하는지, (b) **숨김 중 B 선택**(모바일 패널에서 B 좌표·주소로 고른 경우)을 미뤘다가 지도 화면에서 1회 실행, (c) **숨김 중 맞춤 버튼 요청**("두 위치 모두 보기"가 요청된 상태로 화면이 바뀐 경우)의 미루기, (d) 비교 완료 조건 3행.

**점포 정보창 배치 — 검증 항목 (A3 NAVER 검수 스파이크 관찰, 2026-10-14)**

**SDK 제약 때문에 정책 변경이 필요한 항목은 없다.** 비교 맞춤 기준 zoom 13은 검수 결정으로 유지한다(태블릿·모바일의 4.8km 비교는 "B만 + 버튼").

## 4. 8-D 전제 — 반경 300·500·1,000m (엔진 트랙, 보류)

이 장은 8-D를 시작할 때 지켜야 할 전제다. 엔진·golden·API·공용 캐시는 바꾸지 않았고, 엔진 트랙은 **보류**다(검수 결정 2026-10-14). 재개 시점은 사용자 결정이다.

### 4.1 왜 엔진 변경인가 (B안)
- 반경은 엔진 `config.RADIUS_M = 500` 하나로 묶여 있다. `radius_demand.radius_profile`·`build_reference`는 이미 `radius_m` 파라미터가 있지만, `scoring.py`가 raw `반경m`과 `meta.분석반경_m`을 `C.RADIUS_M`에서 출력하므로 **반경을 바꿔도 응답에는 500으로 찍힌다**(실험 확인). adapter에서 meta만 덮어쓰는 방법은 pass-through 원칙(D-012)과 충돌해 쓰지 않는다.
- A안(지도 탐색 범위만 조절, 점수는 500m)은 "반경별 분석" 요구를 충족하지 못하므로 만들지 않는다. 지도 원은 분석 반경 하나만 그린다.
- 방식: `scoring_engine/v0_4/` = v0.3 사본 + 최소 diff(`RADIUS_OPTIONS_M = (300, 500, 1000)`, `analyze(..., radius_m=None)`이 받은 값을 meta·raw에 기록, `엔진버전 = "mvp-0.4"`). 원본·`v0_3/`·v0.3 golden·매니페스트는 그대로(D-006).

- 경쟁성 미산출(29업종 중, 300/500/1000): 부평역 0/0/0 · 구월3동 1/0/0 · 송도2동 14/6/0 · 강화읍 1/1/1.

### 4.3 분석 조건 키와 결과 캐시 (frontend 세션 메모리)
- 조건 키 `K = (lat, lng, biz_code, radius_m)`. 요청·응답 대조(`matchesRequest`)에 `result.meta.분석반경_m === radius_m` 추가, 점포 응답도 반경 대조.
- 캐시 항목 `{analyze: AnalyzeResponse, nearby: NearbyStoresResponse | null}`, LRU 12. 적중이면 요청 0.
- **저장은 활성 요청의 성공 응답만.** seq가 지난(늦은) 응답은 지금 규칙("첫 줄에서 seq 불일치면 return") 그대로 **캐시에도 저장하지 않는다**(늦은 응답 캐싱은 2차 검토).
- 분석 성공·점포 실패 = `nearby: null` 부분 캐시. 그 키로 돌아오면 분석은 즉시, 점포만 재요청. 점포 "다시 시도"는 점포만(성공하면 캐시 채움). 분석 실패는 저장 안 함.
- 조건 변경(취소)은 캐시를 지우지 않는다. 응답 `엔진버전`이 세션 첫 응답과 다르면 전체 폐기.
- 표시: 점수·근거·점포·마커는 **활성 K의 응답이 있을 때만** 그린다(이전 반경 결과를 남기지 않음). 지도 원만 선택 즉시 새 반경.

### 4.7 성능·lock 검증 조건
- 유지: 업종 1개 cold ≤ 15s, 두 번째 warm ≤ 0.5s, entry 29/14, 29개 ≤ 180s, `load_runtime` ≤ 15s — 500m 기준 그대로.
- 참고 실측(겹침 보장 없는 1차 실험): 87개 (업종, 반경) 순차 build 176.0s(건당 1.93~2.37s). warm 중 cache hit 대기 11.8s, warm 중 cold 2.12s — **참고값**. 재측정은 `build_reference`를 감싸 "build 시작" `Event` + `Barrier(2)`로 동시 출발을 보장하고 "요청 시각 − 직전 build 시작 시각"을 함께 기록한다.
- lock 방식별로 구조상 없어지는 대기와 남는 대기: (A) hit 경로 lock 없음 → hit가 **lock을 기다리는 일은 없어진다**. 그래도 warm 스레드의 계산(pandas)과 GIL·CPU를 나눠 쓰므로 hit 응답 시간의 상한을 구조만으로 보장하지는 못한다 — 50ms는 측정으로 확인할 **목표 기준**이다. (B) miss 전역 lock → cold 대기 **상한 없음**(warm이 lock을 연속 재획득). (C) miss 키별 lock → cold ≤ 자기 키 build 1회 × 경합 계수(측정 필요). (D) warm 양보 → "진행 중 build + 자기 build".
- 검증 조건: (A) warm 중 hit ≤ 50ms를 측정으로 확인(가짜 느린 build 2s + Barrier — 가짜 build는 GIL을 쥐는 실제 계산이 아니므로, 실제 `build_reference` warm 중 p95도 따로 기록하고 그 값이 50ms를 넘으면 기준을 다시 정한다). (B) 유지 시 상한을 주장하지 않고 p95만 기록. (C) 채택 시 cold ≤ 2 × 단독 build(계수는 실측 뒤 조정), warm 전체 +20% 이내. 공통: golden 29/29·`test_cached_recomputation_is_identical`.
- 8-D2a(공용 캐시 hit 경로 수정, 골든 중립)는 **이번 범위 밖**이다. 운영 첫 `/analyze` 약 4.5초(D-018, 원인 미확정)와는 연결하지 않는다.
