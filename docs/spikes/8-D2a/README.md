# 8-D2a ReferenceCache 잠금 측정

## 판정 (2026-10-17)
- **캐시 동시성·기능**: Codex 재검수 통과 — hit 잠금 없음, miss 직렬화, 같은 키 1회, 실패 시 미저장·대기자 해제, warm 확인·예약 원자성.
- **성능 — hit 비차단**: 확인했다. 근거는 구조(hit 경로가 build 잠금을 잡지 않음)와 회귀 테스트(다른 build를 멈춘 채 hit 완료)다.
- **성능 — 실제 API 지연**: 아래 측정값을 기록만 한다. 50ms 달성이나 새 상한을 주장하지 않는다.
- **warm 시간 증가**: 요청 없는 교차 3쌍 모두 수정본이 느렸고, 원인은 확인하지 못했다. 이 단위는 운영 성능을 승인하거나 최적화를 마쳤다고 주장하지 않는다.
- **추적 항목** (`docs/TASKS.md` 8-D2b): v0.4 운영 전환 전에 warm 증가의 원인·영향과 실제 서버(uvicorn·Cloud Run)의 성능을 확인한다.

변경(`scoring_engine/reference.py`):
- **hit**: 잠금 없이 읽는다.
- **miss**: build 실행권 하나로 한 번에 하나씩 계산하고, 같은 키는 1회만 계산한다.
- **warm 양보**: background warm은 실행권을 기다리는 요청이 있으면 실행권을 얻지 않는다.

2차(Codex 검수 반영, 2026-10-17): 실행 중 여부(`_building`)와 대기 요청 수(`_foreground_waiting`)를 `Condition` 하나(`_state`)가 지킨다. 그래서 warm의 "대기 요청 확인"과 "실행권 예약"이 같은 잠금 안에서 한 번에 일어난다. 1차 구현은 둘 사이에 틈이 있어, 그 틈에 들어온 요청이 있어도 warm이 먼저 계산할 수 있었다.

대기 요청들 사이의 순서(FIFO)는 보장하지 않는다. 점수·엔진 사본·golden은 바꾸지 않았다. 배경은 `docs/UX_REDESIGN.md` 4.7, 결정은 `docs/DECISIONS.md` D-024에 있다.

## 성능 기준 (검수 합의안)
- **캐시 hit 비차단**은 측정값이 아니라 두 가지로 검증한다.
  - 구조: hit 경로는 build 잠금을 잡지 않는다.
  - 회귀 테스트: 다른 키의 build를 `Event`로 멈춰 둔 상태에서도 hit가 끝난다(`tests/test_reference_cache_lock.py`).
- 캐시 직접 조회 시간과 API(`/analyze`) 응답 시간은 따로 잰다.
- API 중앙값·p95·최대는 기록만 한다. 지금 자료로 50ms 달성이나 새 지연 상한을 주장하지 않는다.
- warm 비용 비교는 요청 없는 같은 조건에서, 변경 전·후 순서를 바꿔 가며 반복 측정한다(`scripts/bench_warm_ab.py`).
- 요청 부하를 넣는 비교는 요청 수와 도착 일정을 같게 한다(`scripts/bench_cache_lock.py` v2).

## 실행 조건 (공통)
- 환경: Windows 11(10.0.26200), Python 3.10.11, 논리 CPU 16, 한 PC에서 측정 사이에 다른 무거운 작업 없이 차례로 실행.
- 클라이언트: FastAPI `TestClient`(in-process — uvicorn·네트워크 없음).
- 비교 대상 "변경 전" = 커밋 `93b7031`의 `reference.py`(전역 lock). `scripts/ref_impl.py`로 git에서 불러오며, 작업 트리 파일은 바꾸지 않는다.

## v2 측정 (2026-10-17, 현재 기준) — `results/v2_*.json`

### 1. 같은 요청 부하에서의 응답 시간 — `scripts/bench_cache_lock.py` v2, 엔진 v0.4

```bash
SCORING_ENGINE_VERSION=v0_4 python scripts/bench_cache_lock.py --impl working --out docs/spikes/8-D2a/results/v2_working_v0_4.json
SCORING_ENGINE_VERSION=v0_4 python scripts/bench_cache_lock.py --impl 93b7031 --out docs/spikes/8-D2a/results/v2_base_v0_4.json
```

요청 일정은 두 구현에서 같다.
- 앱 시작(전체 background warm 시작) 직전을 0초로 한다.
- 0~60초 동안 0.25초마다 **정해진 시각에** 측정 요청을 스레드로 하나씩 보낸다(앞 요청이 끝나기를 기다리지 않는다).
- 짝수 번째는 캐시 직접 조회(`ReferenceCache.competition`, 미리 계산한 키 `R10406`·500m), 홀수 번째는 같은 키의 API hit(`POST /analyze`)다.
- 10·25·40초에는 아직 warm되지 않은 키의 API cold 요청을 보낸다.
- **보완(2026-10-17, Codex 재검수 지적)**: 저장된 v2 결과를 만든 스크립트는 cold 요청을 예정 시각 전에 시작했다. 실제 시작 시각은 다음과 같다(예정보다 약 0.25초 이르다).
  - 변경 전: 9.757 / 24.752 / 39.758초
  - 수정본: 9.759 / 24.756 / 39.753초
  - 두 실행에서 같은 방식으로 일찍 보냈으므로 도착 일정은 서로 같다. 다만 표의 "10·25·40초"는 예정 시각이고, 일반 요청 1건(수정본, 예정 60.0초)도 0.2ms 일찍 시작했다.
  - 스크립트는 이제 요청 스레드가 자기 예정 시각까지 기다린 뒤 실행 직전에 상태와 시작 시각을 기록한다. 짧은 실행(v0.3, 10초, cold 2·5·8초)으로 요청 44개 모두 시작 ≥ 예정임을 확인했다(차이 0.001~0.043초, cold 실제 시작 2.005·5.013·8.014초).
  - **저장된 v2 결과는 보완 전 스크립트로 잰 것이며, 다시 재지 않았다**(파일 그대로 보존).
- 결과: 캐시 121개, API hit 120개, cold 3개.

원본(`raw`)에 남기는 것:
- 요청마다 예정·시작·종료 시각, 그리고 **그 요청이 시작될 때**의 build 진행 여부와 직전 build 시작 뒤 경과 시간(`since_build_start_at_start`).
- build마다 키와 시작·종료 시각.
- 요약에서 "겹침"은 요청 구간 [시작, 종료]가 build 구간과 실제로 겹친 것이다.

| 항목 (v0.4) | 변경 전 `93b7031` | 수정본(작업 트리) |
|---|---|---|
| 캐시 직접 조회 — 전체 중앙값 / p95 / 최대 (n=121) | 1,981 / 5,611 / 8,303 ms | 0.0 / 0.1 / 0.1 ms |
| 　그중 build와 겹친 요청 | n=115, 중앙값 2,107 ms | n=107, 중앙값 0.0 ms |
| API hit `/analyze` — 전체 중앙값 / p95 / 최대 (n=120) | 2,956 / 7,654 / 12,529 ms | 82.4 / 110.0 / 226.4 ms |
| 　그중 build와 겹친 요청 | n=120, 중앙값 2,956 ms | n=108, 중앙값 82.1 ms |
| 　build와 겹치지 않은 요청 | n=0 | n=12, 중앙값 84.4 ms |

| warm 완료 시각(0~60초에 위 부하 포함) | 205.3 s | 287.7 s |

읽는 법:
- **캐시 직접 조회는 수정본에서 build와 겹쳐도 0.1ms 안이다.** 비차단의 근거는 위 회귀 테스트이고, 이 값은 참고다.
- **API hit 응답 시간(중앙값 82ms, p95 110ms, 최대 226ms)은 기록만 하고 상한으로 주장하지 않는다.**
  - 경합이 없을 때는 같은 요청이 35ms라, 4.7의 "≤ 50ms"는 이 자료로 달성했다고 하지 않는다.
  - 겹치지 않은 요청(n=12)의 분포가 겹친 요청과 비슷한 이유는 확인하지 않았다.
- **같은 부하에서 수정본의 cold 요청과 warm 완료가 더 늦었다.** 원인은 확인하지 않았다.
  - 가능한 설명: 변경 전에는 hit 요청이 잠금에서 쉬며 기다렸고, 수정본에서는 hit 요청 120개가 바로 실행되면서 build와 CPU·GIL을 나눠 쓴다. 검증한 것은 아니다.
  - 표본은 각 1회다.

|---|---|---|---|---|

- **3쌍 모두 수정본이 느렸다.** 원인은 확인하지 않았다.
- 수정본이 build마다 더하는 잠금 처리(`_acquire_build`+`_release_build`)는 따로 재면 호출당 약 1.3µs다(요청 없음, 10만 회 평균). warm 1회의 build 58번이면 0.1ms 미만이라 이것만으로는 초 단위 차이를 설명할 수 없다.

- 1차에 기록한 "요청 없는 warm 12% 차이"(`bench_reference.py`, 변경 후 2회 → 변경 전 2회)도 원인이 확인되지 않았다. 이번 교차 측정도 원인을 밝히지 않는다.

## v1 측정 (2026-10-17 1차, 보존) — `results/before_v0_4.json`, `after_v0_4.json`, `after_v0_3.json`

1차 구현(확인·예약 사이 틈이 있던 버전)과 변경 전 코드로 잰 결과다. 파일은 그대로 두며, 아래 한계 때문에 **비교·결론에 쓰지 않는다.**
- 측정 한 번에서 build 진행 여부를 **캐시 직접 조회 직전에 한 번만** 읽어, 이어서 실행한 API 요청에도 같은 값을 썼다. 그래서 API 요청의 "build 중" 분류가 실제 겹침과 다를 수 있다.
- 다음 측정은 앞 측정이 끝난 뒤 0.2초 쉬고 보냈다. 그래서 변경 전은 측정 하나가 수 초씩 막혀 표본이 36개뿐이었고, 수정 후는 약 1,000개였다. 요청 수와 도착 일정이 달라 warm 시간과 부하 비교가 공정하지 않다.
- `since_start`(직전 build 시작 뒤 경과)는 수집만 하고 결과 파일에 저장하지 않았다. 1차 문서의 "기록한다"는 설명은 틀렸다.
- 1차 수치(build 중 cache hit 3.1s → 0.01ms, API hit 중앙값 3.35s → 79ms)는 1차 구현 기준이다.
- 1차의 요청 없는 warm 비교(`bench_reference.py`, v0.3 29개, 각 2회): 변경 전 평균 95.3초, 1차 구현 106.8초다. 순서를 교차하지 않았고 원인도 확인하지 않았다.

## 측정하지 않은 것
- uvicorn·Docker·Cloud Run 같은 실제 서버와, 네트워크를 거친 요청.
- 실제 사용 패턴의 동시 부하(여러 cold 요청 동시 등).
- 부하 측정의 반복 분산(각 1회), 엔진 v0.4의 요청 없는 warm 교차 비교(v0.3만 했다).
- warm 시간 차이의 원인(build 단위 시간 분석·프로파일링은 하지 않았다).
