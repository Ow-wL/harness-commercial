# 8-D2b 성능 확인 — warm 시간 증가의 원인·영향 (2026-10-18, Claude 로컬 측정 · 로컬 측정·분석 검수 통과)

> 검수(2026-10-18): **로컬 측정·분석 검수 통과**(Codex 재검수) — Codex 직접: 관련 테스트 8건 통과, 서버 종료 테스트 추가 3회 연속 통과, 가짜 서버 잔류 0, 보호 경로 변경 없음, `git diff --check` 통과. Codex는 전체 check와 장시간 측정을 재실행하지 않았다 — 전체 check(9단계, 마지막 1회 통과)와 모든 성능 측정값은 Claude 로컬 실행 결과다. 운영 성능 승인·최적화 완료·운영 전환 승인이 아니다. 운영 v0.4 전환 전 필수 조건(vCPU 1·1Gi 조건 측정, 컨테이너 메모리 확인, 시작 직후 cold 지연 수용 판단)은 미완료.

목적: v0.4(반경 300·500·1,000m) 운영 전환을 판단할 근거를 만든다. 운영 배포·Cloud Run 변경은 하지 않았다. 제품 코드·성능 기준·엔진 사본·golden은 바꾸지 않았다. 앞선 측정(`docs/spikes/8-D2a/`)의 스크립트와 원본 결과는 그대로 두었다.

"변경 전"은 커밋 `93b7031`이다. 8-D2 API는 들어 있고 `ReferenceCache`는 8-D2a 이전(전역 lock) 버전이다. "수정본"은 8-D2a 이후 코드다(작업 트리 = `892f908`).

지연 상한이나 성능 개선 완료를 주장하지 않는다. 모든 값은 한 기계에서 나온 분포다.

## 실행 조건 (공통)
- Windows 11(10.0.26200), Python 3.10.11, 논리 CPU 16. 측정은 겹치지 않게 한 번에 하나씩 차례로 돌렸다. 다른 무거운 작업은 없었다.
- 변경 전 구현은 두 방식으로 불러왔다.
  - in-process 측정: `scripts/ref_impl.py`로 git에서 `93b7031`의 `reference.py`를 불러온다.
  - uvicorn 측정: `93b7031`을 임시 git worktree로 꺼내 그 서버를 띄웠다. worktree는 측정 뒤 지웠다.

## 1. warm 을 build 단위로 분해 — 요청 없음, 순서 교차 (`scripts/bench_warm_builds.py`)

```bash
SCORING_ENGINE_VERSION=v0_4 python scripts/bench_warm_builds.py --a 93b7031 --b working --pairs 2 --out docs/spikes/8-D2b/results/warm_builds_v0_4.json
SCORING_ENGINE_VERSION=v0_3 python scripts/bench_warm_builds.py --a 93b7031 --b working --pairs 3 --out docs/spikes/8-D2b/results/warm_builds_v0_3.json
```
측정 조건은 다음과 같다.
- 한 프로세스에서 같은 RuntimeData를 쓰고, 실행마다 새 캐시를 만든다. 앱과 같이 background thread에서 `cache.warm()`을 돌린다.
- 키마다 기록하는 것: 캐시 메서드 구간(경과 시간·스레드 CPU 시간), 실제 계산 구간(`build_reference` 또는 `site_profile` 158회의 합), 그 둘의 차이(오버헤드), 동시에 진행 중인 build 수.
- 엔진 함수는 감싸서 시간만 재고, 결과는 그대로 돌려준다.

| 엔진 | 쌍 | 순서 | 변경 전 전체 | 수정본 전체 | build 중앙값(변경 전/수정본) | `build_reference` 비중 | CPU/경과 | 오버헤드(변경 전/수정본) |
|---|---|---|---|---|---|---|---|---|
| v0.4 (87) | 0 | 변경 전 → 수정본 | 245.58 s | 245.52 s | 2.709 / 2.716 s | 0.97 | 0.99 | 0.286 / 0.282 s |
| v0.4 (87) | 1 | 수정본 → 변경 전 | 265.94 s | 263.73 s | 2.858 / 2.840 s | 0.97 | 0.98~0.99 | 0.296 / 0.302 s |
| v0.3 (29) | 0 | 변경 전 → 수정본 | 123.01 s | 108.78 s | 3.775 / 3.375 s | 0.91~0.92 | 0.96~0.98 | 0.344 / 0.338 s |
| v0.3 (29) | 1 | 수정본 → 변경 전 | 101.78 s | 100.64 s | 3.147 / 3.169 s | 0.91 | 0.98 | 0.302 / 0.304 s |
| v0.3 (29) | 2 | 변경 전 → 수정본 | 116.74 s | 76.72 s | 3.614 / 2.260 s | 0.91 | 0.97~0.99 | 0.360 / 0.216 s |

- 키별 `build_reference` 시간 비율(수정본/변경 전)은 v0.4 87개에서 중앙값 0.998(0.77~1.21), v0.3 29개에서 중앙값 0.818이었다. v0.3에서는 수정본이 3쌍 모두에서 빨랐다(108.78 < 123.01, 100.64 < 101.78, 76.72 < 116.74초 — 처음 보고의 "3쌍 중 2쌍"은 잘못 적은 것이다). 이것도 실행마다 큰 편차 안의 값이며 수정본이 빠르다는 근거로 쓰지 않는다.
- 반경별 평균 build 시간(v0.4 쌍 0): 300m 2.65~2.67초, 500m 2.69~2.70초, 1,000m 2.84~2.86초.
- 동시 build 수는 모든 실행에서 최대 1이다. 경합이 없는 조건이다.
- 엔진 계산 자체의 CPU 시간이 실행마다 달라지는 폭(v0.3 키 하나 2.26~3.78초)이 구현 차이보다 훨씬 크다.

- 이미 계산된 키는 수정본에서 잠금을 기다리지 않는다. 다만 hit 응답(중앙값 87~98ms)은 warm이 끝난 뒤(43~53ms)보다 길다.

## 4. 메모리 (`scripts/bench_memory.py`, Windows 전용)
- v0.3: RuntimeData 로드 뒤 working set 178.2MiB, 29개 warm 뒤 178.8MiB, 최대 197.1MiB.
- v0.4: 로드 뒤 178.0MiB, 87개 warm 뒤 140.2MiB, 최대 196.4MiB.
- private bytes는 약 600~640MiB(최대 696MiB)다. Windows commit 기준이라 numpy·BLAS 예약분이 들어간다.
- Linux 컨테이너 RSS와 같은 값이 아니다. 운영 1Gi 대비 판단에는 컨테이너 측정이 필요하다.
- 측정 중 실수: 처음 실행에서 ctypes 핸들 타입을 지정하지 않아 0이 기록됐다. 그 파일은 지우고, 타입을 지정한 스크립트로 다시 쟀다.

## 측정 스크립트 보완 (2026-10-18, Codex 검수) — 위 결과는 보완 전 스크립트로 측정했다

검수에서 측정 실패를 정상 결과처럼 남길 수 있는 문제가 나왔다. 스크립트를 고쳤고, 위 표의 결과 파일은 보완 전 스크립트로 잰 것이라 **덮어쓰거나 다시 재지 않았다.**

- `scripts/bench_warm_builds.py`:
  - background warm의 예외를 호출 측으로 다시 던진다.
  - warm 뒤 캐시 항목 수와 실제 build 수가 기대와 같은지 확인한다(competition = 업종 수 × 엔진 반경 수, location = 업종들의 유인시설 집합 수).
  - 실패하면 결과 파일을 쓰지 않고 종료 코드 1로 끝난다.
- `scripts/bench_uvicorn.py`:
  - 대기마다 기한을 둔다(준비 120초, 첫 키 600초, 전체 warm 1,800초). 대기 중 서버 프로세스가 끝났는지 확인한다.
  - warm `failed`와 정상 `done`을 구분한다. `/health` 엔진 광고가 요청한 엔진과 같은지 확인한다.
  - 모든 측정 요청(warm 뒤 30회 포함)의 상태 코드와 오류를 기록한다. 지연 통계는 200 응답만으로 내고 오류는 `errors`에 따로 둔다.
  - 결과에 `valid`·`invalid_reasons`를 적고, 무효면 종료 코드 1로 끝난다.
- 자동 테스트 `tests/test_bench_scripts.py`(8건, 실제 엔진·데이터 없이 가짜 캐시·가짜 서버 `tests/bench_fixtures/`):
  - 다루는 상황: warm 스레드 예외, 캐시 미완성, 정상 실행, warm failed, HTTP 503, 첫 키 대기 초과, 엔진 광고 불일치, 서버 종료.
  - 수정 후 8건이 통과한다. 보완 전 사본에 같은 테스트를 돌리면 8건이 실패한다. 실패 이유는 결과 저장·종료 코드 0, 무한 대기로 인한 90초 시간 초과, `valid` 필드 없음이다.

- 재검수 보완(2026-10-18): 서버 종료 테스트가 시간 경합으로 가끔 `http_errors`가 되던 문제(가짜 서버 exit 모드가 warm 완료를 먼저 보여 줄 수 있었음)를 고쳤다. exit 모드는 warm을 첫 키만 끝난 상태로 두고(`done` 없음), 측정 요청 6건을 모두 정상 처리한 뒤의 첫 `/health` 호출에서 끝난다. 단언은 넓히지 않고 좁혔다(무효 사유 `server_exited` 하나, 오류 요청 0, 측정 요청 모두 200). 반복 확인: 종료 테스트 10회 연속 통과, 8건 전체 3회 통과, 남은 가짜 서버 0.

**기존 결과의 사후 확인** — 저장된 원본에서 확인한 범위:
- warm 분해 10회(v0.4 4회·v0.3 6회): 모두 캐시 통계와 실제 build 수가 기대값과 같다(87/14·29/14). warm 예외나 미완성 실행은 없었다.
- uvicorn 4회: 첫 `/health`의 엔진 광고는 `mvp-0.4`, 모든 `/health` 기록에 warm `failed` 없음, 최종 87/87 완료, 측정 요청(hit 241 + cold 3) 244건이 모두 200이다.
- TestClient 부하 4회: 측정 요청 244건이 모두 정상이다. warm 뒤 30회는 그 스크립트가 200이 아니면 중단하므로 정상이었다.

**사후에 확인할 수 없는 범위:**
- uvicorn의 warm 뒤 30회 요청의 상태 코드(보완 전 스크립트는 지연만 기록했다).
- 대기 중 서버 프로세스가 재시작됐는지(측정 요청이 모두 200이라 끝나지는 않은 것으로 보인다).

## 운영(v0.4) 전환 판단에 남은 조건
1. **Cloud Run과 같은 조건(vCPU 1, 1Gi)에서 warm 시간과 warm 중 응답을 측정한다.** Docker에서 `--cpus 1 --memory 1g`로 측정하거나, 무트래픽 리비전에서 측정한다(`docs/UX_REDESIGN.md` 4.6 ③). 로컬 값(약 5분)이 운영과 같다는 근거가 없다.
2. **시작 직후 cold 지연을 받아들일지 결정한다.** 운영은 `min-instances 1`(D-018)이라 warm은 배포·재시작 때만 일어난다. 그동안 아직 계산되지 않은 키는 5~10초(로컬 관측)가 걸릴 수 있다. warm은 500m를 먼저 끝낸다. 로컬 uvicorn에서는 500m 29개가 135~146초에 끝났다(부하 포함). 8-D2a v0.3 1회 측정의 29개 warm은 112.9초였고, 조건이 같지는 않다. 300·1,000m 첫 요청은 그 뒤 약 2.5~3분 더 cold일 수 있다.
3. **컨테이너 메모리(RSS)가 1Gi 안인지 확인한다**(로컬 Windows 값만 있음).
4. 이전 관측의 warm 차이 원인(기계 상태로 추정)은 미확인으로 둔다. 8-D2a 캐시 변경이 warm을 늦춘다는 근거는 이번 교차 측정에서 나오지 않았다.
