## R1 [P1] 인쇄 레이아웃이 화면용 고정 패널에 잘려 일부 내용만 출력된다

**위치:** `frontend/src/styles/print.css:18~54`, 관련 `frontend/src/main.tsx:7~8`, `frontend/src/App.css:162~178,254~261`.

**직접 확인:** 현재 HEAD의 소스로 `node e2e/build.mjs` production 빌드를 다시 생성했다. 실제 Edge(headless)의 print 미디어와 A4 PDF 출력으로 단일 PC방 결과를 확인했다. API는 기존 v0.3 fixture로 대체하고 외부 요청은 차단했으며 실제 지도·검색 API는 호출하지 않았다. 엔진의 점수 의미가 아닌 동일한 제품 CSS와 DOM의 인쇄 동작을 확인한 검사다.

1280×800에서 print 미디어의 `.panel`은 여전히 x=860,y=20,width=400,height=760인 화면용 패널이었다. 네 탭은 `display:block`이 되어 각각 약 699·630·2417·908px 높이로 존재했지만 문서 scrollHeight는 800이고 PDF는 1페이지만 생성됐다. 캡처에는 결과 상단과 일부 관점만 나타나며 이후 탭·현장 카드·출처는 아래에서 잘린다. 375×812에서도 패널 높이 744px, 문서 높이 812px로 같은 현상을 측정했다. 다크 패널 배경과 밝은 제목 글자도 남는다.

**원인:** print.css의 `.app`, `.panel`, `.workspace__panel` 재정의가 실제 번들에서 뒤의 화면 CSS 및 모바일 선택자에 밀린다. `@media print`는 자체로 선택자 우선순위를 높이지 않는다. `main.tsx`에서 print.css가 App의 CSS보다 앞서 로드되는 구조도 관련된다. print 규칙의 존재만 확인하는 문자열 테스트로는 잡히지 않는다.

**영향:** 사용자에게 인쇄 완료로 보이는 PDF에서 핵심 결과·현장 메모·데이터 출처가 누락된다. ‘한 페이지’가 된 것이 정상 압축 결과가 아니다.

**수정 방향:** print CSS의 로딩 순서와 우선순위를 정리하고, 패널·조상의 position/height/max-height/overflow 및 인쇄 색 토큰을 실제 print 미디어에서 재정의한다. 모든 탭을 출력할 것인지, 1페이지 요약과 별도 부록을 만들 것인지도 명시한다. 탭 전체의 총량을 고정 높이로 잘라 한 페이지를 맞추면 안 된다. React 아코디언은 `open && ...`로 내용 자체를 생성하지 않으므로, 세부지표까지 인쇄할 정책이면 CSS만으로는 펼칠 수 없다.

**재검증:** 다크/라이트, 좁은 화면/데스크톱에서 PDF를 생성하고 마지막 현장 카드·메모·자료 기준일·면책이 포함되는지 확인한다. 한 페이지 수만 확인하지 않는다.

**영향:** 같은 탭을 열어 둔 동안 데이터 묶음·엔진이 교체되면 사용자가 명시적으로 다시 분석해도 예전 세션 캐시가 반환된다. 새 요청을 보내지 않으므로 서버 버전 변경도 발견하지 못하면서 ‘저장 당시 결과가 아니라 지금 서버의 결과’라고 안내한다. 저장된 스냅샷과 메모리 캐시는 서로 다르지만, 어느 쪽도 현재 서버에 재계산을 요청한 결과는 아니다.

**수정 방향:** 명시적인 보관함 재분석에는 캐시 우회 또는 새 서버 버전 확인 경로를 둔다. 다른 반경을 오가는 일반 캐시 정책은 유지할 수 있다. 서버가 같은 버전일 때 캐시를 재사용하려면 서버를 확인한 사실과 재계산 여부를 안내 문구에 정확히 반영한다.

**렌더 재현:** 검수용 ErrorBoundary로 SavedSites를 감싼 뒤 그 항목의 보관함을 열었다. `Cannot read properties of undefined (reading 'toFixed')`가 발생해 경계의 오류 화면으로 바뀌었다. 누락된 overall을 formatScore에 넘기는 지점에서 먼저 실패한 것이다. p.key와 stores.toLocaleString도 검증되지 않은 값을 읽는다. 실제 App에는 보관함을 감싸는 해당 복구 경계가 없다. 로그는 `repro-render.log`에 남겼다.

**발생 조건:** 정상 UI만 사용하면 반드시 생기는 문제라는 뜻은 아니다. 브라우저에 남은 손상/부분/과거 형식의 로컬 저장 데이터를 안전하게 읽겠다는 명시적 정책의 결함이다.

**수정 방향:** 저장 데이터 전체 스키마를 검증하고 잘못된 항목만 제거한다. 유한한 좌표·반경, nullable 점수, 점포수, 관점 원소, 버전 필드를 확인한 뒤 렌더한다. localStorage를 읽는 다른 새 기록 경로도 null/배열/부분 객체를 점검하면 좋다.

**재현:** `review-repro.test.tsx`의 `R4` 테스트. 손상 항목 필터 단언에서 실패한 뒤, 실제 SavedSites 렌더 검사까지 보강해 오류 화면으로 바뀌는 것도 재현했다. 두 검수 실행 모두 3건 실패이며 제품 코드를 수정한 후의 재검증은 아니다.

검사 환경 이력도 남긴다. 최초 병렬 vitest 실행은 Windows 샌드박스 임시 변환 파일 ENOENT로 8개 suite 로드에 실패(1개 suite 3건만 통과)했다. 저장소 안 TEMP/TMP 및 maxWorkers=1로 위 222건이 통과했다. 백엔드 첫 실행은 샌드박스에서 TestClient 단계가 진행되지 않아 중단했고, 일반 로컬 실행에서 80건이 통과했다. 타입 검사·lint도 직접 통과했다. 이번 검수는 최종 소스 전체 check 및 정식 E2E 재실행을 대신하지 않는다. 수정 후 확정한 배포 후보에서 전체 check와 정식 E2E가 필요하다.

}
