기준: `c48a686` (`33d0625` R1 본체 + 테스트·자료). 요청에 따라 ① UI/UX 디자이너, ② 사용자, ③ 개발자 관점으로 순서대로 검수했다. 제품 코드는 수정하지 않았다. **판정: 수정 후 재검수 필요. P1 3건, P2 5건.** 배포·운영 전환은 수행하지 않았다.

## 1회 — UI/UX 디자이너 관점

**기본 방향은 좋으나, 세련된 대시보드로 마무리됐다고 보기는 어렵다.** 종합 점수와 등급의 우선순위, 색과 글자 등급의 병용, 상세 근거의 점진적 노출, 라이트·다크의 일관성은 유지할 가치가 있다. 업종 카드도 숫자 정렬과 현재 업종 표시가 명확하다.

가장 큰 문제는 정보 밀도와 공간 배분이다. 넓어진 패널에 비해 제목 아래 여백·관점 행 높이·고정 하단 버튼이 커서 핵심 점수가 화면 아래로 밀린다. 작은 거미줄은 큰 막대 목록의 세로 중앙에 놓여 윗부분이 비어 보이고, 아래쪽은 스크롤 가림 효과에 걸린다. 모바일에서는 같은 점수를 두 그래프로 반복하면서 거미줄을 먼저 보여준다. **막대 목록을 기본으로 먼저 보여주고, 좁은 화면의 거미줄은 접거나 보조 보기로 옮기는 편을 권한다.** 상세는 R1-4.

- [1366×768 일반 분석](review-r1-evidence/desktop-normal.png): 공유 안내가 없어도 관점 3개만 온전히 보인다.
- [1366×768 다크](review-r1-evidence/desktop-dark.png): 색 체계는 일관되나 정보 밀도 문제는 같다.
- [375×812 공유 링크 분석](review-r1-evidence/mobile-375.png): 첫 화면에는 관점별 숫자가 하나도 보이지 않는다.
- [640×800](review-r1-evidence/tablet-640-fresh.png): 지도와 점수 카드가 폭을 과하게 나누고, 상단 조작을 패널이 가린다(R1-2).

비차단 다듬기: 떠 있는 상단 칩·지도 카드의 그림자를 약하게 통일하고, 본문 11~12px 보조 문구의 가독성을 높일 것. “PC방이(가)” 같은 조사 템플릿, “타겟”, “종사자”, “기본 가중치”는 각각 자연스러운 조사·“주요 손님층”·“주변 직장인”·“기본 계산 기준” 등으로 다듬을 여지가 있다. 과한 장식이나 새 UI 라이브러리를 추가할 필요는 없다.

## 2회 — 사용자 관점: 수정할 지적

### R1-1 [P1] 시간대 카드가 엔진 해석과 반대로 안내한다

- 위치: `frontend/src/lib/timeInsights.ts:39–49`, `scoring_engine/v0_5_1/scoring.py:55–66,190–193`.
- 실제 재현: 부평역 `(37.4894,126.7246)`, 500m, PC방. 카드: **“주된 영업 시간대(저녁)와는 엇갈려요”**. 같은 응답의 시장성 flags: **`영업시간대_유입_집중`**. 원래 엔진 공식의 `time_fit`은 약 **1.3235**, 집중 기준 `>1.20`이다.
- 같은 위치의 29업종을 실제 API로 대조하니 당구장·치킨·세탁소 등 **11업종**에서 같은 방향의 모순이 발생했다. [전체 수치](review-r1-evidence/semantics.json).
- 원인: 24시간 분포의 겹침을 비교하는 대신, 길이가 다른 네 구간의 총량 중 최댓값 구간 이름만 비교한다. 피크 구간이 다르다고 두 분포가 엇갈리는 것은 아니다. 균등 분포도 8시간짜리 밤 구간이 가장 커지는 편향이 있다.
- 수정: 구간 비중은 설명용으로 유지하되, “겹친다/엇갈린다/유리하다”는 엔진의 기존 시간대 적합도·flags와 같은 기준으로 안내한다. 데이터가 충분하지 않으면 두 피크가 다르다는 관찰만 쓰고 적합도를 단정하지 않는다. 점수 엔진은 변경하지 않는다.
- 재검증: PC방 1.3235 사례, 실제 11업종, 균등 분포, 유입 피크만 다르지만 겹침은 큰 사례, 미산출. 현재 테스트는 구간명 비교를 정답으로 고정해 이 결함을 통과시킨다.

### R1-3 [P1] 같은 이미지 배포만으로는 이미 열린 구버전 탭을 보호하지 못한다

- 위치: `backend/app/main.py:499–503`, `frontend/src/api/schemas.ts:382` 부근의 `/analyze` 응답 계약.
- 검수 자료에서 알려진 `insights` strict 호환성 문제다. 다만 **프런트·백엔드를 같은 이미지로 배포한다는 대응은 새로 방문하는 사용자만 보호한다.** 배포 전에 열려 있던 탭의 JavaScript는 그대로 실행되고, 다음 분석 요청부터 새 서버의 응답을 받는다. `index.html`의 `no-cache`도 열린 탭을 갱신하지 않는다.
- 직접 검증: 이전 소스 `c9a2f08`의 실제 `AnalyzeResponseSchema`로 새 서버 응답을 검사하면 `Unrecognized key: "insights"`로 실패한다. 같은 응답에서 `insights`만 제거하면 통과한다. [결과](review-r1-evidence/contract.json).
- 수정: 구버전 요청에는 기존 응답 형태를 유지하고 신버전 요청이 설명 자료를 명시적으로 요청하도록 하거나, 버전이 구분된 새 엔드포인트를 사용한다. 새 프런트에서만 strict를 완화하는 것은 이미 열린 구버전 탭의 해결책이 아니다.
- 재검증: 이전 번들을 연 상태에서 서버만 새 버전으로 전환 → 분석·반경 변경. 롤백 시 신버전 번들/구버전 서버도 확인한다.

### R1-5 [P2] 모든 관점이 낮아도 한 줄 결론이 “좋다”고 말한다

- 위치: `frontend/src/lib/conclusion.ts:71–80`.
- 경계 입력 재현(실제 위치 측정값이 아닌 합성 점수): 다섯 관점 `[24,20,15,10,5]`, 최고=시장성·최저=안정성 → **“시장성은 좋지만…”**. 최고점도 주의 등급인데 긍정 평가한다. `[35,34,33,32,31]`처럼 모두 약함 등급인 경우도 fallback은 “…가 가장 좋은 자리예요”다.
- 원인: 약점 `<25` 분기와 마지막 분기가 최고점의 절대 수준을 확인하지 않는다. 규칙을 충실히 구현했더라도 사용자에게 내리는 결론은 잘못될 수 있다.
- 수정: 상대적으로 높은 관점과 절대적으로 좋은 관점을 구분한다. 전반적으로 낮으면 그 사실을 우선 말하고 “그중 상대적으로 높은 관점은…”으로 안내한다. “같은 업종이 많다/역에서 멀다/폐업이 잦다”도 복합 점수 하나만으로 원인을 확정하지 말고 해당 근거가 뒷받침할 때만 쓴다.
- 재검증: 모든 점수 <25, 모두 25~39, 일부 미산출, 강점만 70 이상, raw와 복합 점수의 방향이 다른 경우. 금지어 검사 외에 문장의 사실성을 검증한다.

### R1-6 [P2] 업종 순위가 한 번 실패하면 같은 조건에서 복구할 수 없다

- 위치: `frontend/src/lib/useRank.ts:30–47`, `frontend/src/components/RankCard.tsx:34–37`.
- 재현: `/rank` 한 번만 네트워크 오류로 처리 → 비교 시작 → 취소하여 같은 단일 결과로 복귀. 요청은 **총 1회**, 계속 오류 문구만 남는다. 재시도 버튼도 없다. [재현 결과](review-r1-evidence/edge.json).

- 수정: 자동 무한 반복은 막되 명시적 “다시 시도”와 실패 상태 초기화 경로를 제공한다. 로딩/완료는 별도 `aria-live="polite"` 영역으로 안내할 수 있다. 여러 `role=status`가 존재한다는 이유만으로 필요한 상태 알림을 제거할 필요는 없다.
- 재검증: 네트워크 실패→복구→같은 조건 재시도 성공, 반복 클릭 요청 제한, 이전 요청 취소 및 늦은 응답 폐기.

### R1-7 [P2] 인쇄에서 기존 관점별 근거가 사라지고 지도용 여백이 남는다

- 위치: `frontend/src/components/PerspectiveScores.tsx:167–194`, `frontend/src/styles/print.css`, `frontend/src/App.css:668–670`.
- 재현: 관점을 펼치지 않은 기본 결과를 print media로 전환. `.perspective__evidence` DOM **0개**, 결과 머리 `padding-right:360px`. 지도는 인쇄에서 숨겨져도 이 여백은 유지된다. 정렬 버튼과 업종 “전체 보기”도 종이에 남는다. [값](review-r1-evidence/edge.json).
- 이전에는 존재하던 근거 DOM을 새 `expanded && ...` 조건이 만들지 않는다. CSS로 숨은 탭을 펼쳐도 존재하지 않는 근거를 복원할 수 없다. 이는 새 카드 인쇄 추가의 미착수와 별개로 **기존 인쇄 결과의 회귀**다.
- 수정: 인쇄용 근거를 별도 렌더하거나 인쇄 수명주기에 맞춰 전체 근거를 생성한다. print에서 지도 예약 padding/min-height 및 화면 조작 요소를 해제한다. 업종 목록을 상위 5개만 인쇄한다면 그 범위를 명시한다.
- 재검증: 기본 접힘 상태·펼침 상태·다크·모바일의 인쇄 결과를 비교. 이번에는 print media/DOM만 확인했으며 실제 종이 페이지 분할·인쇄 대화상자는 검증하지 않았다.

### R1-8 [P2] 키보드로 지도 확대·복귀하면 포커스가 body로 사라진다

- 위치: `frontend/src/App.tsx:926–928,1483–1491`.
- 재현: “지도 크게 보기”를 focus 후 Enter → `document.activeElement.tagName === 'BODY'`. “결과로 돌아가기”를 focus 후 Enter → 다시 `BODY`. [실측](review-r1-evidence/flows.json).
- 새 배치로 바뀌며 누른 버튼이 언마운트되지만 새 포커스 위치를 지정하지 않는다. 키보드 사용자는 결과/지도에서 연속 작업하기 어렵다.
- 수정: 확대 시 “결과로 돌아가기” 또는 지도 영역으로, 복귀 시 호출한 지도 버튼 또는 결과 제목으로 포커스를 명시적으로 옮긴다. 스크롤 위치도 보존한다.
- 재검증: 클릭뿐 아니라 Enter·Space·Tab으로 확대/복귀 반복, 스크롤 후 “지도 보기”, SDK 실패, 모바일 지도/결과 전환.

## 3회 — 개발자 관점

**유지할 것:** 표시용 점수 정렬과 엔진 계산의 분리, 실제 raw 값의 인용, 미산출을 0으로 처리하지 않는 방향, 지도 DOM 유지, 백엔드 LRU 상한, 기존 ResultCache의 버전 방어. 보호 경로의 R1 변경도 없었다.

**수정 순서:** R1-1(해석), R1-2(조작 차단), R1-3(배포 계약)을 먼저 해결하고 R1-4~8을 함께 재검수할 것을 권한다. 템플릿·시간대 오류를 AI 설명으로 덮지 말고 기본 해석부터 바로잡아야 한다.

추가할 최소 방어:

1. `/rank` 캐시가 비어 있을 때 동일 키 요청을 합치는 처리. `rank_lock`은 조회·저장 구간만 보호하며 29업종 계산 구간(`main.py:546–553`)은 밖에 있어 같은 키 동시 요청이 중복 계산될 수 있다. reference 캐시의 중복 방어와 전체 rank 계산의 중복 방어는 별개다. 이번에는 부하 측정하지 않았으므로 운영 지연 수치는 단정하지 않는다.
2. rank 프런트 캐시에 크기 상한과 데이터·엔진 버전 무효화. 현재 Map은 좌표·반경만 key이고 `clearRankCache()`는 제품에서 호출되지 않는다. 기존 결과 캐시는 버전이 바뀌면 비우는데 순위는 과거 값이 남을 수 있다. `/rank`에도 엔진 식별 계약을 맞추는 편이 좋다.
3. 위 8개 재현을 회귀 검사로 추가. 테스트 개수보다 실제 클릭 가능 여부·문장과 데이터의 일치·열린 구버전 탭·인쇄 DOM을 확인하는 것이 필요하다.

불필요하게 늘리지 않을 것:

- 모바일의 거미줄/막대 동시 상시 노출, 화면마다 반복되는 긴 면책 문장, 일반 사용자용 “기본 가중치” 같은 용어. 필요한 제한은 해당 수치 가까이에 짧게 설명하고 자세한 근거는 펼친다.
- 29업종에 대형 검색 라이브러리·차트 라이브러리를 추가할 필요는 보이지 않는다. 기존 native select와 작은 SVG 구현을 유지할 수 있다.
- 비교 거미줄·보관함의 새 스냅샷·AI 기능은 합의된 후속 범위로 둘 수 있다. 다만 인쇄 회귀(R1-7)를 후속 기능으로 묶어 지나치면 안 된다.
- 역 제안은 [지원하지 않는다는 안내 바로 아래 실제 역 칩이 나타난다](review-r1-evidence/station-suggest.png). 주소/역 이름 지원 범위를 안내에 반영하고, 정확히 입력한 “부평역”을 “부평구청역”보다 먼저 제안하면 이해하기 쉬워진다.
